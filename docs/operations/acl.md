# アクセス制御（ACL）

[ロール](auth.md)（`reader` / `writer` / `admin`）はクエリ全体に対して「読み取りだけ」「書き込みも可」を決めます。
ACL を使うと、さらにラベル単位・プロパティ単位で、特定のユーザーやロールに読ませない・書かせないようにできます。

- 読めないラベルのノードは、そのユーザーからは**存在しないもの**として扱われます（エラーにはなりません）
- 読めないプロパティは値が無いもの（`null`）として扱われます
- 書けないノード・プロパティを変更しようとすると、その文はエラーになり、文の変更はすべて取り消されます
- `admin` ロールには ACL は適用されません（誤って管理者を締め出さないため）

ACL は認証を有効にしたサーバー（`--require-auth`）でだけ働きます。認証なしのサーバーでは、全員が admin として扱われるため制限はかかりません。

## 規則を設定する

規則の設定と一覧は admin だけが実行できます。ユーザー管理の文と同じく、サーバーで処理されます（REPL や埋め込み利用ではエラーになります）。

### DENY

読み取り（`READ`）または書き込み（`WRITE`）を禁止します。

```cypher
// writer ロールには :Secret のノードを見せない
DENY READ ON :Secret TO ROLE writer
```

```cypher
// :User の password プロパティは reader に見せない
DENY READ ON :User(password) TO ROLE reader
```

```cypher
// bob は :Invoice のノードを変更できない
DENY WRITE ON :Invoice TO USER bob
```

対象の書き方は 3 種類です。

| 対象 | 意味 |
|---|---|
| `:Label` | そのラベルを持つノード（とそのすべてのプロパティ） |
| `:Label(prop)` | そのラベルを持つノードのプロパティ `prop` |
| `:*` | すべてのノード（ラベルの無いノードを含む） |

主体は `TO USER ユーザー名` か `TO ROLE ロール`（`reader` / `writer` / `admin`、別名も可）です。存在しないユーザーは指定できません。

### GRANT

禁止の例外として、明示的に許可します。ロールで禁止したものを、特定のユーザーにだけ許すときに使います。

```cypher
// reader にはすべてを見せず、:Public だけを見せる
DENY READ ON :* TO ROLE reader
```

```cypher
GRANT READ ON :Public TO ROLE reader
```

上の 2 つは同じロールに対する規則なので、`DENY` が優先され、`:Public` も見えません（次の「判定のしかた」を参照）。
ロールの禁止をユーザー単位で開けるのが `GRANT` の使いどころです。

```cypher
// reader は :Report を見られないが、alice だけは見られる
DENY READ ON :Report TO ROLE reader
```

```cypher
GRANT READ ON :Report TO USER alice
```

ACL はロールの権限を広げません。`reader` のユーザーに `GRANT WRITE` を付けても書き込みはできません。

### REVOKE

同じ主体・対象・操作の規則（`GRANT` と `DENY` の両方）を取り除きます。

```cypher
REVOKE READ ON :Report FROM ROLE reader
```

同じ主体・対象・操作に `GRANT` と `DENY` を両方は置けません。後から設定したほうに置き換わります。

### SHOW ACL

```cypher
SHOW ACL
```

規則ごとに `subject`（`USER bob` / `ROLE read_only` など）、`resource`（`:Secret`、`:User(password)`、`:*`）、`action`（`READ` / `WRITE`）、`permission`（`GRANT` / `DENY`）を返します。

## 判定のしかた

あるユーザーがあるラベル（またはプロパティ）を読める・書けるかは、対象に当てはまる規則から次の順に決まります。
`:*` の規則はすべてのラベルに、`:Label` の規則はそのラベルのすべてのプロパティにも当てはまります。

1. そのユーザーを名指しした規則があれば、それだけで決める（1 つでも `DENY` なら禁止、`GRANT` だけなら許可）
2. 無ければ、そのユーザーのロールに対する規則で同じように決める
3. どちらも無ければ許可

ノードに複数のラベルがあるときは、どれか 1 つでも読めなければノード全体が見えません。

## 適用される範囲

### 読み取りの禁止

- `MATCH` のパターンに一致しない（`count(*)` やラベルごとの件数にも含まれない）
- 見えないノードとつながるリレーションシップも見えない
- `CALL db.labels()`、アルゴリズム（`db.pageRank` など）、全文検索（`db.index.fulltext.search`）の結果にも出ない。全文検索は、索引の対象に読めないプロパティを含むノードを返さない
- 読めないプロパティは `n.prop` が `null`、`keys(n)` / `properties(n)` にも出ない。`WHERE n.prop = …` や `{prop: …}` でも一致しない
- ACL が適用されるセッションでは、プロパティ索引による絞り込みを使わない（読めない値で一致してしまうため）。結果は同じですが、遅くなることがあります

### 書き込みの禁止

`CREATE`・`MERGE`・`SET`・`REMOVE`・`DELETE` などで、書けないラベルのノード（ラベルの追加・削除を含む）、書けないプロパティ、書けないノードにつながるリレーションシップを変更すると、文全体が `access denied: …` のエラーになり、変更は取り消されます。

- 読めないプロパティも書けません（見えない値を上書き・削除させないため）
- 見えないノードとつながっているノードは削除できません（`DETACH DELETE` でも）。`DETACH` なしの `DELETE` は、見えないリレーションシップがあれば通常どおり削除されません
- インデックス・制約の作成と削除は ACL の対象外です（ロールの権限だけで決まります）

### 注意点

- 読めないノードは見えないので、`MERGE` は一致するノードが無いと判断して新しく作ります。一意制約があれば、制約違反のエラーで既存のノードがあることが分かります
- 規則はサーバーごとの設定です。レプリケーションのフォロワーには伝わらないので、同じ `--users-file` を置いてください
- シャーディングでは各シャードのサーバーで適用されます

## 保存と監査ログ

規則は `--users-file` のファイルにユーザーと一緒に保存されます（ファイルの `version` は 3。以前の version 2 のファイルは規則なしとして読み込み、次の保存で 3 になります）。
ユーザーを `DROP USER` すると、そのユーザーを名指しした規則も消えます。`--users-file` が無いときはメモリ上だけで、再起動すると消えます。

`--audit-log` を指定していると、規則の追加・削除は `acl_changed`、ACL で拒否された書き込みは `permission_denied`（`"action":"acl_write"`）として記録されます。
