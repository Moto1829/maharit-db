# 193: 書き込み中に読み取りが待つ範囲を狭める

## 問題

書き込み文は制約・全文検索・プロパティ索引の write ロックを文の間ずっと持ち、読み取りは同じロックの read を取るので待つ。
書き込み 2 接続が走っている間、軽いクエリは p50 2.23 ms / p99 5.01 ms（負荷なしは 0.30 / 0.44 ms）。

計測は task182 のベンチ（`bash scripts/run_bench_local.sh`、2026-11-16、10 コア）。

## 進め方

- 索引を使わない読み取りがロックを取らずに済むか、書き込み側がロックを索引更新の間だけ持てるかを検討する
- 文の途中の状態が読み取りから見える範囲（今も `ConcurrentGraph` 自体は途中の状態が見える）を整理してから決める
- task185（実行スレッド）の後に測り直す

## 完了の目安

- `LAT light (2 batch writers)` が負荷なしに近づく
- 変更の前後を `scripts/perf_check.py` で比べ、他の項目が遅くなっていないこと

## 結果（2026-11-21、完了）

整理したこと:
- 書き込み文は制約・全文索引・プロパティ索引の write ロックを文の間ずっと持つ（索引と制約の検査を文の中で一貫させるため）。読み取りは 3 つ全ての read ロックを取っていたので、書き込みが 1 文終わるまで待っていた
- `ConcurrentGraph` 自体は、書き込み文の途中の状態が読み取りから見える（これまでと同じ。ロックはグラフを守っていない）。なので、読み取りが使わない管理対象のロックを取らなくても、見える結果は変わらない

直したこと:
- 読み取りの文が使いうるものだけロックを取る。判定はクエリの文字列から、使う可能性があれば取る側に倒す:
  制約は `CONSTRAINT` を含むとき、全文索引は `fulltext` か `index` を含むとき、プロパティ索引は `index` を含むか、
  索引の張られたプロパティ名が現れるとき。使わないものは空の管理対象を渡す
- 索引の張られたプロパティ名は、プロパティ索引とは別の小さなロックで持ち、DDL とスキーマの適用のたびに更新する

結果（変更前後のバイナリを交互に 3 回ずつ。書き込み 4 接続が 200 件ずつ CREATE を続ける間の、索引を使わない軽い読み取り）:
- p50 0.12 → 0.09 ms、p99 0.46 → 0.17 ms（負荷なしは p50 0.09 / p99 0.15）。3 秒間の読み取り件数 約 18,600 → 約 32,200

残る制限: 索引を使う読み取り（例: 索引のある `n.id = 7`）は、書き込みが索引の write ロックを持つ間は待つ。
これを無くすには索引を複数版で持つ（MVCC）か、書き込みが索引を更新する間だけロックを持つ構造に変える必要があり、別タスクの規模になる。
