# 192: 書き込みのスループット（WAL の待ちとグループコミット）

## 問題

`CREATE` 1 件が 1 接続で 3 ms（330 件/秒）。エンジンは 2.66 µs なので、ほぼ WAL の fsync 待ち。8 接続でも 948 件/秒（2.9 倍）で、グループコミットが効ききっていない。
WAL のレコードは JSON、CRC32 は 1 ビットずつ計算する自前実装。

計測は task182 のベンチ（`bash scripts/run_bench_local.sh`、2026-11-16、10 コア）。

## 進め方

- 8 接続で伸びない理由を調べる（fsync 1 回に何件まとまっているか、`write_gate` を持つ時間）
- CRC をテーブル引きにする（依存を足さずにできる）。レコードのバイナリ化は形式の変更なので、旧形式の読み込みを残す
- macOS の fsync は遅いので、Linux でも測って判断する

## 完了の目安

- `PARALLEL CREATE x8` が x1 の 8 倍に近づく
- 変更の前後を `scripts/perf_check.py` で比べ、他の項目が遅くなっていないこと

## 結果（2026-11-21、完了）

調べたこと（macOS、10 コア、`--wal fsync`）:
- fsync 1 回あたりの件数を数えるカウンタを WAL に足した（チェックポイントのたびに info ログに出る）。8 接続で CREATE を続けると、1 回あたり平均 1.7 件しかまとまっていなかった
- 原因: WAL への追記（`write`）を書き込みゲートの中で行っていた。macOS では同じファイルの fsync（`F_FULLFSYNC`）の最中の `write` が待たされるため、fsync の間に次の書き込みがゲートの中で止まり、後ろの書き込みが積み上がらなかった

直したこと:
- `--wal fsync` では、追記はメモリのバッファに積むだけにし、`sync_to`（ゲートの外）がバッファを書いて fsync する。応答は従来どおり自分の記録が fsync された後。書き込みか fsync が失敗したら、以後の `sync_to` は全てエラーにする
- CRC32 を 1 ビットずつの計算から表引きにした
- `--wal os` はこれまでどおり追記のたびに `write` する（プロセスが落ちても残す必要があるため）

結果（変更前後のバイナリを交互に 6 回ずつ、同じ条件で測った中央値）:
- 8 接続の CREATE: 約 930 件/秒 → 約 1,425 件/秒（+53%）、fsync 1 回あたり 1.7 → 5.5 件。32 接続では 3,684 件/秒
- 1 接続は変わらない（約 360 件/秒。fsync 1 回 ≒ 2.8 ms が下限）
- 書き込み中の軽い読み取りの応答時間も変わらない（p50 0.08 ms / p99 0.44 ms）

`run_bench_local.sh` の 1 回ずつの比較は macOS の fsync のばらつきが大きく（同じバイナリで x1 が 340〜560 件/秒）、判断に使えなかった。
Linux では測っていない。fsync が速い環境では、ゲートの中の処理（実行と WAL への追記）の時間がより効いてくる。
レコードのバイナリ化（JSON をやめる）は形式の変更が要る割に、fsync が支配的な今は効果が小さいので行わない。
